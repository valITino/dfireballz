# DFIReballz Cases Directory

Case working directories live here, one per investigation, named after the
case number generated by the orchestrator (`DFIR-<year>-<NNN>`).

## Canonical layout

Each case follows the six-phase forensic process model defined in
[`docs/forensic-process.md`](../docs/forensic-process.md). The on-disk
layout mirrors the phase order so the directory tree itself is the audit
trail.

```
cases/
└── DFIR-2026-001/
    ├── 01-readiness/
    │   └── case-precondition.json
    ├── 02-identification/
    │   └── evidence-records/
    ├── 03-acquisition/
    │   ├── acquisition-manifest.json
    │   └── <evidence-id>/
    │       ├── <evidence-id>.dd
    │       ├── <evidence-id>_acquisition.log
    │       └── <evidence-id>_verification.log
    ├── 04-examination/
    │   ├── extraction-manifest.json
    │   └── <evidence-id>/
    ├── 05-analysis/
    │   ├── findings.json
    │   └── timelines/
    └── 06-reporting/
        └── closure-manifest.json
```

Phases:

| # | Phase | What goes here |
|---|---|---|
| 01 | Readiness | Case preconditions, MCP health snapshot, pinned tool versions, time-source attestation |
| 02 | Identification | Evidence records: ID, type, source, photographs, authority, acquisition order |
| 03 | Acquisition | Forensic images, hashes, write-blocker docs, acquisition + verification logs |
| 04 | Examination | Extracted artifacts, parsed structures, indexes — derived from acquisition copies, never originals |
| 05 | Analysis | Findings, timelines, IOC enrichment, hypothesis evaluation, citations to evidence + audit IDs |
| 06 | Reporting | Closure manifest, final hash re-verification, audit-log digest, case-closed CoC entry |

## Loopback (revisions)

When a phase has to be re-entered (e.g. analysis reveals a missing evidence
source), the new pass writes into a revisioned subdirectory rather than
overwriting the original:

```
04-examination/         ← original pass
04-examination-rev2/    ← second pass after loopback
04-examination-rev3/    ← third pass, and so on
```

Every loopback is recorded as a chain-of-custody entry documenting the
source phase, target phase, and reason. See the loopback policy in
[`docs/forensic-process.md`](../docs/forensic-process.md).

## Where things still live outside the case directory

- **Final reports:** `reports/<case-id>/` (deliverables — Markdown, HTML,
  PDF). Produced in phase 06 from the case directory's analysis output.
- **Read-only originals:** `evidence/<case-id>/`. Mounted read-only into
  every container. Originals are never touched after acquisition.
- **Session-level output:** `output/` — host-visible findings,
  screenshots, logs, exports, timelines that aren't tied to a specific
  case (or that are produced before a case is opened). See
  [`output/README`](../output/README).

## Compatibility note

Older prompt templates reference flat subdirectories like
`cases/<case-id>/notes/`, `artifacts/`, `timelines/`. Those remain valid
for ad-hoc working files and will not be removed mid-flight. New work
should follow the phase layout above; existing templates will be migrated
in a follow-up slice.
